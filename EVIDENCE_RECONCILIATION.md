# ABDS Evidence and Reconciliation Profile v0.6

> Trust model for gateway observations, Provider reports, signed Provider evidence, late usage, and compensating corrections.

## 1. Principle

ABDS distinguishes what a gateway observed from what the AI Provider reports and settles.

```text
estimated
    -> gateway_observed
        -> provider_reported
            -> reconciled
                -> final
```

No intermediary may promote its own estimate to Provider-authoritative evidence without Provider support.

## 2. Evidence hierarchy

### 2.1 Provider-signed

The Provider signs an individual Usage Event, settlement receipt, or verifiable batch manifest.

This is the provider-native target because the Provider controls execution, measurement, pricing, and the charged funding bucket.

### 2.2 Provider-reported

Evidence comes from an authenticated Provider API response, usage endpoint, billing export, or invoice record but is not signed in the ABDS format.

The gateway MUST preserve the Provider request or billing reference used for reconciliation.

### 2.3 Gateway-attested

The gateway records the request it sent, the response it received, and any locally observed usage.

Gateway evidence is provisional. It proves what the gateway asserts, not what the Provider independently settled.

## 3. Provider-signed evidence

A signed evidence object SHOULD bind:

```text
issuer
provider_request_id
provider_event_id
delegation_id
client_id
request_id
attempt_id
usage quantities
funding bucket
pricing snapshot
occurred_at
payload digest
signature metadata
```

Production signatures SHOULD be asymmetric and support:

- issuer discovery;
- key identifiers;
- key rotation;
- revocation or compromise handling;
- deterministic canonicalization;
- replay detection;
- verification failure reporting.

High-volume Providers MAY sign a batch manifest or Merkle root instead of each event, provided each event has a verifiable inclusion proof.

## 4. Reconciliation Event

A Reconciliation Event compares an earlier quantity with later Provider evidence.

Required values include:

```text
source_usage_event_id
provider_request_id
original_quantity
provider_final_quantity
adjustment_quantity
unit_type
funding_bucket_ref
status
action
```

The invariant is:

```text
adjustment_quantity = provider_final_quantity - original_quantity
```

A zero difference produces `no_change`. A non-zero difference produces `adjustment_required` or a dispute.

## 5. Late and corrected usage

Late Provider evidence MUST NOT rewrite the earlier Usage Event or settlement.

```text
Original Usage Event
        ↓
Late Provider evidence
        ↓
Reconciliation Event
        ↓
Compensating Ledger adjustment, when required
```

The adjustment MUST:

- reference the prior event;
- use a unique idempotency key;
- preserve the original funding bucket;
- preserve or reference the applicable pricing basis;
- avoid duplicate charging;
- record actor, reason, and timestamp.

## 6. Variance states

```text
matched
variance_detected
adjusted
disputed
final
```

Provider policy MAY define rounding tolerances, but the tolerance MUST be documented and cannot hide material variance.

## 7. Missing and unmatched records

Implementations SHOULD detect:

- Provider charge with no gateway event;
- gateway event with no Provider record after the reconciliation window;
- duplicate Provider report;
- Provider record mapped to the wrong Client, grant, or funding bucket;
- late evidence after final reporting;
- repeated adjustment for the same variance.

Unmatched records enter a recoverable investigation state. They MUST NOT be silently charged twice.

## 8. Dual attribution

High-volume execution remains attributable to both:

```text
delegated principal / Beneficiary
        +
registered Client
        +
workload or workflow
```

An individual user must not appear to be the sole source of traffic generated by application retries, routing policy, speculative execution, background jobs, or agent loops.
